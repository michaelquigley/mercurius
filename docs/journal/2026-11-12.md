## sessions-on-disk stage 2: built

Stage 2 is in the working tree, uncommitted. Stage 3 is not started. Terminus was `clean`; its one advisory finding was `df-binding` on the new `outlived_server` tag, covered by the standing veto (the `bind-project-data-through-dd` card owns it).

Where the build reads the work order rather than following it to the letter:

- The work order puts the runner's start-up sequence in the `run-round` command: close-on-exec on descriptor 3, rebuild the lock, lock the OS thread, `Run`. It lives in `runner.RunInherited` instead, and the command only calls it. The process tests re-execute the test binary as the runner, so this way they run the same sequence production does. A test that reimplemented it would pass with the real command broken.
- `mcpserver.New` takes `Options` with an optional `Launcher`; nil means the process launcher. The process launcher starts `os.Executable()`, which inside a test binary is the test binary, so any test that builds a server through `New` and starts a round has to pass the in-process launcher.
- The three reviewers start their process through one shared `reviewer.RunCommand` (prepare, `Start`, `Started`, `Wait`) rather than each calling `Start` and `Wait` themselves.
- `docs/current/README.md` is not in stage 2's docs list; one line in it said rounds run inside the server process, and that line was corrected.

Things a later change could break without a test noticing:

- Nothing tests that the runner locks its OS thread. The failure it prevents, the Go runtime retiring the thread and the kernel killing a healthy reviewer, cannot be produced on demand. Both launchers lock the thread and `Run`'s doc comment says why. Do not remove either because nothing fails.
- `internal/runner`'s process tests own the package's `TestMain`, which switches on `MERCURIUS_TEST_ROLE` to become the runner, a stand-in server, or a sleeper. A test binary gets one `TestMain`; a second one anywhere in the package breaks every process test.

Verified with the real codex reviewer (`gpt-6.1-sol`), built to a temporary path: killing the server five seconds into a round left the runner and reviewer running, the round completed with `outlived_server: true`, and a new server collected it. Not verified on any platform but Linux; the lifetime arrangements are a no-op elsewhere.

## sessions-on-disk stage 3: built

Stage 3 is in the working tree, uncommitted; the close-out has not started and waits for Michael's acceptance. Terminus was `clean`; its one advisory finding was `df-binding` on the new reviewer-source fields, under the standing veto. The `.gitignore` change in the tree is Michael's, not part of the stage.

Decisions a later change could undo without seeing why:

- The user-level file is read on every call even when the project has a `reviewer_override`, so a broken user file fails every tool in every project. An override could have skipped the read; the call was to surface a broken installation file at once rather than hide it behind an override until the override comes out.
- Nothing aimed at agents names `reviewer_override`: not the refusal of a plain `reviewer` block, not the project template's comment, not the tool descriptions, not `agent-guide.md`. An agent that hits the refusal should remove the block, and a key it has just been shown is the one it will rename the block to. `configuration.md` and `user-guide.md`, written for the operator, do name it. Keep it that way.
- The old guard for the `reviewers` array said "renamed to `reviewer`", which would now steer straight into the new refusal. It points at the user-level config like the `reviewer` refusal does.
- Config errors are `config.FileError`s naming the file at fault, so the broker can say which of the two files to fix: `config_path` with "read mercurius.yaml", or `user_config_path` with "read the user-level config".
- `newRootCommand` takes the user-level path; only `main` calls `config.UserConfigPath()`. That is what keeps every CLI test off the developer's real file.

Verified that no test reads a real user-level config. With `XDG_CONFIG_HOME` and `HOME` pointed at a planted, unreadable `mercurius/config.yaml`, the whole suite passed. The same trap made the real binary fail, so the trap does bite. With the real binary, a project `mercurius.yaml` with no reviewer ran a round on the user-level reviewer, reported as `user config` in `open_session`, the launch response, and `_run.json`.

The rubric's project description was brought up to date in `terminus-canon`. Four rules the build now depends on have no quality behind them, and are flagged for Michael rather than added:

- mercurius never signals a process by a pid read from disk.
- mercurius reads its json files and never parses its own markdown back.
- nothing writes a running round's `_state.json` without holding the runner lock, and the monitor never writes.
- nothing aimed at agents names `reviewer_override`.

The first two have tests, and so does the monitor half of the third. Nothing tests that a state write holds the lock, and only a careful doc edit protects the last.
