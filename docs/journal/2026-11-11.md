Where the build reads the work order rather than following it to the letter:

- The lock note is written after leftover round directories are removed and the round is numbered, not before as the sequence diagram draws it. The note names the round number, which is not known until then. No crash case changes.
- `runner_pid` and `reviewer_pid` are in the `_state.json` shape and left empty; stage 2 fills them. Under the in-process launcher the runner's pid is the server's, and a launch `conflict` naming it would invite the operator to kill the server.
- `operations.md` already carries the launch-`conflict` section and the residuals, which the work order lists under stage 2's docs, because they describe stage 1 as shipped. One residual is stage-1-only (a server death leaves the reviewer subprocess running). Stage 2 should rewrite that bullet for the parent-death tie, not add a second.
- The error codes now live in `internal/store` and the broker re-exports them: the runner records failures, and the broker imports the runner.

A coupling stage 2 has to keep: the server's lock descriptor must stay close-on-exec. Go opens files with `O_CLOEXEC`, which is why stage 1's reviewer subprocesses never inherit the lock. Checked with the real binary: an orphaned reviewer, still alive after its server was SIGKILLed, did not block the next launch. `ExtraFiles` in the process launcher is the one deliberate exception, and rule 2 of the work order (the runner re-marks it close-on-exec) is what keeps the reviewer from inheriting it there.
