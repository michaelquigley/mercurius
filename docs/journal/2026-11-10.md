# 2026-11-10

## sessions-on-disk replaces the rehydration spec

`docs/future/session-rehydration.md` was deleted on purpose, not lost. It kept the in-memory registry and rebuilt on a miss; Michael wanted the server to hold nothing at all, and the rehydration spec had never been reviewed or given a work order. `docs/future/sessions-on-disk.md` is the replacement. The roadmap card kept its title and filename (`session-rehydration`) because renaming a card is Michael's; only its prompt and log changed.

Two things in the new spec look like they could be simplified and should not be:

- Mercurius never kills a process by a recorded pid. An earlier draft of the design had the server kill an orphaned reviewer by the pid in the round's state; a round can be found dead days later, by which time the pid may belong to something else. The reviewer's death is tied to the runner's by the kernel instead, and the recorded pids are for the operator.
- The launch guard is per log destination, not per session. The per-session check already exists and misses the real duplicate path, which is an agent opening a new session.
- The project override key is `reviewer_override`, and a plain `reviewer` block in `mercurius.yaml` is an error. Accepting `reviewer` as the override would turn every stale template and agent habit into a silent override, which is the thing moving the reviewer to `~/.config/mercurius/config.yaml` exists to stop.

## why the mercurius MCP server shows 'connection closed' between arcs

The server loads `mercurius.yaml` at startup and exits if it is missing. The config is scaffolded per review arc and removed afterward, so in any project with no arc in flight the server dies at launch and the harness reports only a closed connection. Confirmed here by running the server with no config. Scaffolding the file mid-session does not bring an already-failed server back; the harness has to reconnect. The sessions-on-disk spec turns this into a tool error.
