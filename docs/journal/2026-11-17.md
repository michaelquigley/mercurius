## bind-project-data-through-dd: work order drawn

`docs/future/bind-project-data-through-dd-work-order.md` is drafted and unreviewed. There is no spec; the card is the prompt and the work order's first section records Michael's three decisions: take dd's natural shape and let the wire break, write the input schemas to say what is required, and have the config loader refuse unknown keys.

The work order's section on what dd does was checked by running a scratch program against `df` v1.0.6, outside the repo, and is not from dd's documentation. Two of those facts would cost an implementer time to rediscover:

- an explicit `null` bound into an untagged pointer field is an error in forgiving and strict mode alike. Reviewers send `"suggestion": null` on most findings, so the two `Suggestion` fields need `+nullable` or every real review fails to parse.
- a `map[string]any` field tagged `+opaque` carries a raw JSON object exactly, but only under a strict bind. a forgiving bind rounds `9007199254740993` to `9007199254740992` without complaint.

Considered and not done: reproducing today's wire shape exactly with `+nullable` and `+omitempty` on about thirty fields. It would have made the refactor provably shape-preserving, and Michael chose the simpler structs over it.

## the work order dropped its converter

The first draft ported terminus's `json.RawMessage` converter and built a shared codec around it. That was written without testing `+opaque`, which in `df` v1.0.6 already does the job on a `map[string]any` field. The work order now carries the raw reviewer object as a decoded value in an `+opaque` field, with no converter and no shared options, and the schema stage moved ahead of the store stage so the schema package can bind from a decoded value before the store hands it one.

Do not port terminus's converter as a shortcut. Its `ToRaw` decodes through `float64`, so it has the digit loss the opaque route avoids. That is read from its code, not reproduced.

One card went onto `df`'s roadmap, `opaque-accepts-raw-json-fields`: let `+opaque` take a `json.RawMessage` field. Mercurius does not wait on it. An unknown-key reporting feature for `dd` was also considered and deliberately not carded; Michael asked for one change, and mercurius's `+extra` fields do not need it.

## the schema validator reads json.Number as a string

Found in stage 5, when `collect_round` with `round_number: 1` started answering `user_error`. `dd.DecodeStrictJSON` returns numbers as `json.Number`. `jsonschema-go` decides a value's JSON type from its Go kind, and a `json.Number` is a string kind, so `type: integer` refuses it. Its numeric keywords do understand `json.Number`; only the type check does not. Checked in the source at v0.4.2 and v0.4.3, so upgrading does not help.

The adapter therefore validates a copy of the arguments with native numbers and binds from the strict original. Keep both halves: validating the strict tree refuses every integer argument, and binding from the copy would let `1.0` through.

Terminus has the same adapter flow and is not affected only because none of its tool arguments is an integer; its one integer schema is on an output. The day it gains an integer argument it hits this. Read from its code, not run.

## an empty finding id is refused

The first full-repo terminus review found that two findings with `id: ""` passed as a valid review: the schema allowed an empty id and `ValidateUniqueIDs` skipped empty ids on purpose. The exemption dated from 2026-05-06 and no reason for it is recorded. The schema now requires a non-empty id in all three finding arrays, and the uniqueness check has no exemption.

Both halves are kept deliberately. The schema is what stops an empty id at round time; the uniqueness check without the exemption is what holds if the schema is ever loosened, and it is the only check on the path that binds a review from an already-decoded value. Each has its own test, and each test was seen to fail with its half reverted.
